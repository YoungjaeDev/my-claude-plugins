# Hermes native plugin adapter (third runtime)

The shared-source `plugins/<name>/` tree is read by a **third** runtime, Hermes
Agent — alongside Claude Code (native) and Codex 0.135 (generated
`.codex-plugin/plugin.json`). Hermes consumes the same tree in place via native
adapters (`plugin.yaml` + `__init__.py`) that, since PR #84, are **generated by
`scripts/sync-hermes-manifests.mjs`** from `marketplace.json` — the mirror of the
Codex manifest generator, not the `npx skills` install path. `github-dev` was the
hand-written pilot (PR #83); PR #84 absorbed it into the generator and extended
coverage via a `HERMES_ELIGIBLE` allowlist — currently 7 plugins (`github-dev`,
`interview`, `anti-slop-design`, `tcrei-prompt`, `ppt-yeong-style`, `ml-toolkit`,
`brightdata-guide`). The allowlist is the SoT; this page's count goes stale on
every extension, so verify against `scripts/sync-hermes-manifests.mjs`.

> See-also: [[skills-install-wrapper]]

## The adapter = two files in the plugin root

A plugin becomes Hermes-installable by adding, next to its existing
`.claude-plugin/` and `.codex-plugin/` manifests:

- `plugin.yaml` — Hermes manifest, generated from the marketplace entry: `name`, `version`, `description`, `author`, `kind: standalone` (all 5). CodeRabbit (PR #84) repeatedly flagged `author`/`kind` as off-contract, but the "manual-edit drift" rationale is moot once the file is generated + `--check`-guarded, `kind: standalone` is load-bearing, and the working github-dev pilot proves extra fields don't break Hermes — so the generator keeps all 5.
- `__init__.py` — generic Python entrypoint: globs `skills/*/SKILL.md` and registers each as `<plugin>:<skill>` (no per-plugin logic). `yaml.safe_load` is wrapped in `try/except yaml.YAMLError` so one malformed frontmatter can't abort the whole plugin's registration (PR #84 hardening).

Install a single plugin from a monorepo subdirectory:

```bash
hermes plugins install <owner>/<repo>/plugins/<name> --enable
hermes gateway restart   # if Hermes runs behind a messaging gateway
```

Provenance caveats (session 88102e17 upstream re-check, 2026-07-10):

- The monorepo **subpath** install form works empirically but is **undocumented
  upstream** — Hermes docs only show bare `user/repo`.
- Upstream documents `ctx.register_skill(name, path)` as **2-arg**; our generated
  `__init__.py` emits a 3rd `description` arg, which is unverified upstream
  (Python tolerates it only if the signature has a default or `*args` — untested).
- `author:` is not a documented `plugin.yaml` key (likely ignored). `kind` is
  real, enum `standalone|backend|platform|exclusive`.

Before the adapter existed, this install **completed with a warning** — the
plugin had Claude/Codex manifests but no Hermes `plugin.yaml` / entrypoint, so
Hermes registered nothing. The adapter is a thin wrapper; existing Claude/Codex
behavior is untouched.

(Version-sync mechanics — `plugin.yaml` `version`/`description` are derived from
`marketplace.json` by the generator and guarded by `sync-hermes-manifests.mjs
--check` (drift + orphan adapters), so it is no longer a manual three-way sync.
Details in `.claude/rules/plugin-versioning.md`.)

## Update model: `hermes plugins update` is a plain `git pull`

Real-machine output (2026-07-10): `hermes plugins update <name>` on a plugin not
installed as a git clone errors with `Plugin '<name>' was not installed from git
(no .git directory). Cannot update.` Consequences:

- Updates are **git-pull only** — no version compare, no marketplace lookup, no
  cache invalidation. Hermes never reads `plugin.yaml` `version`; that field
  exists solely for our `--check` drift guard.
- A plugin installed by copy (not clone) is frozen at install time; the only
  update path is reinstall.
- In this repo the adapters are **generated but never executed**: CI and
  pre-commit run only `sync-hermes-manifests.mjs --check` (byte-drift), and the
  `hermes` CLI itself never runs. A behavioral break in `__init__.py` (e.g. the
  3-arg `register_skill` above) would pass every guard we have.

## Skills are opt-in: `skill_view`, not bare invocation

Hermes plugin-provided skills are **not** auto-exposed in the system prompt or
`skills_list`. A caller must explicitly load the qualified skill:

```text
skill_view("github-dev:resolve-issue")
skill_view("github-dev:cr-fix")
```

Consequences:

- Quickstart / README examples must show `skill_view("<plugin>:<skill>")`, never
  a bare `github-dev:resolve-issue ...` text/slash line — bare input does **not**
  deterministically load the skill.
- Start a **fresh Hermes session** after `--enable` so the plugin skill registry
  is rebuilt.

## Runtime-portable bodies (extends the shared-source rule)

The same skill bodies run under all three runtimes, so they carry a Hermes
compatibility block mapping Claude/Codex tool names to Hermes tools:

| Claude / Codex | Hermes |
|---|---|
| `Bash` | `terminal` |
| `Read` / `Write` | `read_file` / `write_file` |
| `Edit` | `patch` |
| `Glob` / `Grep` | `search_files` |
| `AskUserQuestion` | `clarify` |
| `Task` | `delegate_task` |
| `Monitor` | `process` |
| `Skill` (list: `skills_list`) | `skill_view` |
| `WebFetch` / `WebSearch` | `web_extract` / `browser_navigate`·`browser_snapshot` |
| image generation | `image_generate` |
| `NotebookEdit` | Hermes "Jupyter Live Kernel" skill, or `write_file`/`patch` on the `.ipynb` JSON |

Bodies that shell out to bundled scripts resolve `SKILL_DIR` in order —
source tree → `$HERMES_HOME/plugins/<name>/...` → `~/.hermes/plugins/<name>/...` —
so one body works whether the plugin runs from the repo or from a Hermes install.

**Layout-divergence caveat**: the two install routes yield different trees. The
plugin route implies `$HERMES_HOME/plugins/<name>/skills/...`, but the only
*measured* Hermes path in this repo is the npx-skills route's flat
`$HERMES_HOME/skills/<skill>/` ([[skills-install-wrapper]], measured
2026-06-24). A body whose fallback chain only covers the plugin route misses
skill-level installs entirely — cr-fix's SKILL.md relies on the un-measured
branch. Fallback chains should cover both layouts until one is verified live.
(PR #84 briefly tried a single `${HERMES_SKILL_DIR}` var for ml-toolkit's
gpu-parallel-pipeline; Codex review caught that the var is undocumented and unset
on a Hermes install → empty path, so it was reverted to this proven 3-branch
fallback. Do not reintroduce `HERMES_SKILL_DIR`.)
