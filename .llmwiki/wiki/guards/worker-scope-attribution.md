# git records state, not who produced it, so worker scope is an isolation problem

An orchestrator that hands slices to parallel workers needs to know which worker wrote which path. The first design asks git: snapshot `git status --porcelain` before dispatch, diff it after, and attribute whatever is new. The snapshot answers a different question. It reports what the tree looks like now, never who made it look that way, and in a shared checkout every worker plus the user writes into the same tree.

Every repair to that design is a patch on one leak, and the leaks do not end:

- **Dirty paths** already present before dispatch belong to the user and must not be reverted, so the baseline must record them — and a worker that edits one of those same files is then invisible.
- **Staged** changes live in the index, which `--porcelain`'s two columns report separately; a baseline read as one string misfiles an `AD` entry.
- **Untracked** files appear as `??` with no history to compare against, so "new" and "changed" collapse.
- **Ignored** files (`.env`, local fixtures) never appear at all. A worker can overwrite one and the snapshot stays identical.
- **Committed** work vanishes from `status` entirely: a worker that commits an out-of-scope file leaves a clean tree.
- **Quoted** paths come back octal-escaped with a non-ASCII or space-bearing name, matching neither the card nor the disk.

Sixteen of seventeen review findings on the guard existed only because of the shared-checkout premise. Patching them one at a time converges on nothing, because the premise is what is wrong.

## Isolation replaces forensics

Give every writing slice `isolation: worktree` and the question stops being "who wrote this" and becomes "what is on this branch". A fresh worktree carries none of the main checkout's uncommitted, untracked or ignored files, so a worker has no path to the user's work except one it builds itself (see the limit below), and the branch is a per-worker record by construction. The check collapses to one command against the slice's recorded base, and each of its three flags closes a hole the obvious form leaves open:

- `git log --no-renames -z --name-only --pretty=format: <base>..<branch>` — two dots and `git log`, **never** `git diff <base>...<branch>`. A diff compares end trees, so a worker that commits an out-of-scope file and deletes it later leaves a clean net diff while the content, a leaked secret included, still rides into history on merge.
- `--no-renames`, because rename detection prints only a rename's destination, so `git mv outside/secret owned/secret` reads as a write inside the card.
- `-z`, because a quoted path matches nothing and turns a legitimate owned file into a false violation.
- A merge commit on the branch is rejected outright first (`git rev-list --merges <base>..<branch>` must be empty): `git log` prints no diff for a merge by default, and a path introduced in a conflict resolution appears in no parent, so it would pass unseen.

A violating branch is not repaired and not reverted — it is simply not merged, which is the property the shared checkout could never offer. Re-querying the same agent is useless here: its offending commit stays in `<base>..<branch>` however it is fixed, so a path violation goes to a newly dispatched agent from the recorded base.

## Isolation costs the inputs it protects

The same emptiness that keeps the user's secrets away from a worker also keeps its `.env`, its fixtures and its `node_modules` away. Those inputs must be supplied into the worktree with the user's approval or regenerated by the repository's own setup step, and a dispatch that can do neither stops rather than sending a worker to fail on a missing file. And because a worktree branches from a commit, an uncommitted input in the main checkout reaches no worker: the user commits it before dispatch — stashing leaves `HEAD` where it was, so every worktree still branches from a base that lacks the input.

## Where a git-level gate stops seeing

The gate reads branches, so it is blind to writes that never become blobs. A worker that creates a symlink under an owned path pointing at a file outside the worktree, writes through it, and removes the link before committing leaves a clean branch log and a clean final tree while the outside file is modified. Rejecting a branch that adds or retargets an escaping symlink closes the persisted case only. The honest statement of the guarantee is that a worktree protects the user's files **from writes that go through git**; a filesystem boundary needs a sandbox, not a branch check.

## Narrowing a guarantee means finding every place it is claimed

The change that scoped this guarantee edited the paragraph that stated it and added the limit to the pitfalls table. Two reviewers, independently, caught the same thing: a *different* section two hundred lines earlier still said the symlink rules "close" the path a worker builds for itself. A document that admits a limit in one place and denies it in another reads as safe wherever the reader happens to land, and the denial is the more reassuring sentence.

The claim to grep for is not the word the finding used. It is every restatement of the guarantee — the summary line, the step that sets it up, the troubleshooting row, the plugin's own `CLAUDE.md` description — because each one was written to be read on its own.
